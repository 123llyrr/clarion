# Realand：体验与技术演进路线

优先级：稳定性、兼容性、低延迟，与视觉效果、动画和交互共同推进。能力状态以代码和验收结果为准；“最先进”是持续目标，不能由功能数量或离屏测试单独证明。

## 第一阶段：性能可观察、动效可控制

当前工作区已接入以下能力，本阶段将其作为一组功能验证：

- 多显示器按照下一次预计呈现时间排列待重绘输出，避免使用哈希表遍历顺序决定先后。
- 物理 TTY 输出会把重绘合并并推迟到预计 KMS 呈现时间前的 latch deadline；渲染预算随成功提交耗时自适应，VRR 空闲后可立即提交。
- `realand msg frame-timings` 和设置面板“概览”提供各显示器最近 240 个样本的 P50、P95、峰值、提交次数、KMS latch 等待和硬件呈现偏差。
- 支持 `content-type` 窗口规则，将应用提交的 `none`、`photo`、`video`、`game` 内容提示用于匹配。动态规则随表面提交更新，初始布局规则仍只在开窗阶段生效。
- 设置面板“外观”增加动画总开关、时长倍数和三个预设。支持移除本地覆盖并恢复继承；设置保存前仍是草稿。
- 关闭动画同时停用旋转渐变和窗口浮动效果。零转速、零宽度的渐变不会因其动画标记持续请求重绘。保留原有配置，重新开启即可恢复。
- IPC 启用 JSON 浮点往返精度支持，保证帧统计序列化后可准确还原。

### 动效预设

| 预设 | 过渡 | 三项 3D 动效 | 适用偏好 |
| --- | --- | --- | --- |
| 流畅 | 标准时长 | 开启弹性窗口、立方体、Glide | 保留空间感与连续过渡 |
| 轻量 | 时长为标准的 0.7 倍 | 关闭上述三项 | 更快完成交互，减少复杂动效 |
| 减少动态 | 关闭 | 总开关停用，细节配置保留 | 对运动敏感、偏好静态桌面 |

轻量预设不等于性能测试结论，也不会关闭客户端自己的动画或全部背景效果。“继承配置”服从 KDL 的合并顺序；如果后面的 include 再次设置同一选项，以最终有效配置为准。

### 性能统计使用

```sh
realand msg frame-timings
realand msg --json frame-timings
```

统计为 CPU 墙钟耗时，含同步等待和调度延迟，不等于 GPU 执行耗时或端到端输入延迟。读取统计不会额外触发桌面重绘。`KMS latch budget`、延后次数与计划延迟分布只在物理 TTY 输出上报告；计划延迟不包含系统定时器的实际唤醒抖动。无硬件时间戳的嵌套会话不报告硬件呈现偏差；VRR 不参与固定刷新逾期比率。

## KMS latch deadline 与 VRR 调度

- 固定刷新输出根据最近的硬件呈现时间和刷新间隔预测下一次呈现，在目标前预留自适应渲染预算。初始预算为刷新间隔的四分之一与 2 毫秒中的较小值，最低 250 微秒；成功提交较慢时立即增大，较快时以 1/16 的步幅缓慢缩小，并为提交保留 250 微秒保护余量。
- 连续更新的 VRR 输出遵守最小刷新间隔并在该期限前开始渲染。输出空闲超过最小间隔后不等待 latch 定时器，直接渲染和提交，让新内容尽快进入下一次可用刷新。
- latch 等待期间的新损伤会合并到同一次唤醒，不会反复推迟期限。输出移除会取消未触发的定时器。已经处于预计 VBlank 兜底状态的无损伤帧沿用原有节奏，避免叠加两套定时器。
- 刷新模式或 VRR 状态变化会取消按旧时序计算的 latch 定时器，保留待处理损伤并按新状态重新调度，避免切换后第一帧仍被旧期限阻塞。
- 该路径仅用于 DRM/KMS TTY 后端；嵌套和无头后端保持立即重绘。算法与定时器状态机已有自动化覆盖，Intel/NVIDIA、多屏混合刷新率和真实 VRR 面板仍需实机测量呈现偏差与延迟。

游戏内容规则示例：

```kdl
window-rule {
    match content-type="game"
    variable-refresh-rate true
}
```

应用必须发送相应内容提示；它不是游戏自动识别器。VRR 仍依赖显示器能力及输出配置。

## FIFO 刷新约束

默认注册 `wp_fifo_manager_v1`（版本 1），无需配置开关。使用该协议的客户端可提交 `set_barrier` / `wait_barrier`；Realand 校验协议对象生命周期并使用 Smithay 的双缓冲状态和提交屏障，再根据渲染结果释放屏障。

- 成功提交的可见帧按主输出释放屏障；TTY 后端下一次提交仍等待 VBlank，避免同一刷新周期连续提交。
- 无损伤帧保存屏障快照，在预计 VBlank 定时器触发时释放。后来的提交不会被旧定时器提前放行。
- 不依赖客户端请求 `wl_surface.frame`，同步子表面的等待约束由 Smithay 按协议忽略。
- 隐藏、未映射、屏幕关闭或无输出时，由每秒一次的兜底定时器释放至少等待一秒的屏障，正常事件循环下约 1–2 秒内推进。移除输出立即释放该输出等待定时器的快照；销毁表面释放其屏障并通知客户端事务队列。
- 兜底机制用于保证进度，不承诺后台帧率。嵌套后端按输出刷新间隔为 FIFO 提供预计刷新定时器，仅为跳过宿主提交的无损伤帧补充节流，普通提交沿用宿主节奏；期限从本轮渲染开始计算，宿主提交已经消耗的时间计入等待。每个输出至多保留一个定时器，重复重绘不推迟期限，输出移除时取消。刷新间隔未知时使用约 16.667 毫秒。该机制不提供精确硬件呈现时间保证。
- 重复创建 FIFO 对象时，`already_exists` 错误归属于 `wp_fifo_manager_v1`；表面销毁后的 `set_barrier` / `wait_barrier` 在 `wp_fifo_v1` 上返回 `surface_destroyed`，销毁对象后可为同一表面重新创建。

真实 Wayland 客户端测试覆盖提交顺序、双缓冲请求、无损伤帧、不同输出、同步/异步子表面、对象与表面销毁、移除输出、关闭屏幕及实际兜底定时器。物理 TTY 的长期运行、VRR 和休眠恢复仍需实机验收。`linux-drm-syncobj-v1` 已在具备 syncobj eventfd 的物理 Vulkan 后端接入；真实 render node/GBM/Wayland 客户端测试已验证 acquire 阻塞和 Vulkan 帧后的 release。物理 TTY 的跨 GPU 与异常路径仍需实机验收。

## 定时提交约束

默认注册 `wp_commit_timing_manager_v1`（版本 1），无需配置开关。Realand 校验协议请求并使用 Smithay 提交屏障；客户端时间戳使用合成器的 monotonic presentation clock，带时间戳的表面提交在目标时刻前保持阻塞，到期后通知提交事务队列。

- 每个表面只维护一个最早期限计时器。更晚的排队提交不会增加计时器，更早的期限会重新调度；期限触发后一次释放所有已到期约束，再自动安排下一个。
- Wayland 的提交顺序保持不变：后来提交的较早期限不能越过先到的较晚期限，未带时间戳的后续提交也不能越过被阻塞的提交。
- 销毁计时器对象不会取消已经提交的约束；销毁表面会取消系统计时器并释放该表面的屏障，避免同一事务中的其他表面停住。
- FIFO 与定时约束可以同时存在，只有两种屏障都解除后提交才会应用。无输出、隐藏或锁屏不会停止 monotonic 计时器。
- 极远未来、系统计时器注册失败等情况由每秒兜底检查重新调度或释放已经到期的约束。非法纳秒值按协议在 `wp_commit_timer_v1` 上返回 `invalid_timestamp`；超出内部有符号时钟范围的秒值保持为不可到达的未来，不会反向溢出成已经过期的期限。
- 同一表面的重复计时器在 manager 对象上返回 `commit_timer_exists`；重复时间戳及表面销毁后的请求分别在 timer 对象上返回 `timestamp_exists` 与 `surface_destroyed`。

当前实现严格保证提交不会在目标时间前应用；它在目标时间到达时才解除阻塞，因此实际呈现可能落到后一个刷新周期。KMS latch 调度已经用于普通输出重绘，但定时提交协议本身仍在时间戳到达时才解锁，目标时间与具体输出也没有协议级绑定；这部分需要结合物理 TTY 的 VRR 与呈现偏差继续调优。

重新登录新版会话后，可用 `wayland-info` 检查 `wp_fifo_manager_v1` 和 `wp_commit_timing_manager_v1` 是否发布。发布 global 的检查仅验证可发现性，提交行为由回归测试验证。
