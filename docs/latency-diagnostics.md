# 输入卡顿与主循环耗时诊断

新版 Clarion 会在单次顶层操作耗时达到 16 ms 时记录 `clarion::latency` 警告。渲染子阶段使用 4 ms 阈值，便于定位多个短阶段叠加造成的慢帧。不包括事件循环空闲等待；无需启用 Tracy 或安装额外分析器。这些阈值是固定的诊断阈值，不代表所有刷新率下的帧预算。

记录以下阶段：

| operation | 测量范围 |
|---|---|
| input-dispatch | libinput 事件进入回调后的处理时间 |
| client-dispatch | Wayland 客户端请求分发 |
| state-refresh | 状态刷新 |
| animation-update | 每轮动画推进 |
| output-render | TTY 输出渲染，包含其中的同步等待 |
| scene-build | TTY 输出的场景元素构建及其中的缓存准备，4 ms 阈值 |
| vulkan-render | 原生 Vulkan 的损伤/平面选择、渲染记录和提交，4 ms 阈值 |
| vulkan-record-submit | Vulkan 命令记录和队列提交，包含准备描述符和驱动调用，4 ms 阈值；不含随后导出呈现 fence |
| vulkan-fence-export | 导出 Vulkan 呈现同步文件的驱动调用，4 ms 阈值；部分驱动可能在此等待生产者 |
| gles-render | GLES 的损伤/平面选择与渲染，4 ms 阈值 |
| kms-submit | 向 DRM/KMS 排队提交帧的调用，4 ms 阈值，不含随后等待显示器呈现 |
| vulkan-dmabuf-import | 未命中缓存时的 DMA-BUF 驱动导入，包括格式查询、映像和内存准备，4 ms 阈值 |
| client-flush | 向 Wayland 客户端刷新事件 |
| producer-fence-wait | GLES/生产者同步点的 CPU 等待 |
| vulkan-fence-wait | Vulkan fence 的 CPU 等待，包括上传/帧积压及完成资源回收 |
| vulkan-resource-cleanup | Vulkan 帧清理，包含锁和未完成提交的等待 |
| config-reload | 配置加载与应用 |

每个阶段、每个线程最多每 5 秒报告一次。`elapsed_ms` 是当前样本耗时，`max_ms` 和 `slow_samples` 汇总自上次报告后的慢样本；`threshold_ms` 和 `thread` 标明该阶段的阈值与线程名称。旧版本日志可能缺少后两个字段。没有后续慢样本时，不会为了打印统计而唤醒主循环。

Vulkan fence 计时位于公共等待入口，覆盖异步提交后的背压与释放等待；同步提交不再外套同一类别的计时，避免一个等待被重复统计。资源清理仍有独立阶段计时，包含锁和其他清理工作。GPU 同步、待处理队列上限及等待超时仍按原有规则执行。

计时测量墙钟时间，包括线程被调度出去的时间。嵌套阶段会重叠，不能把 output-render 与其中的 scene-build、vulkan-render、import 或 fence-wait 相加。异步提交完成前计时便可能结束，不能把 vulkan-render 当作 GPU 执行耗时。input-dispatch 不包含事件在队列中等待的时间；即使该阶段很快，之前的渲染、客户端处理或系统调度仍可能造成输入延迟。

## 使用

先重新登录，确保运行的是带有新诊断的合成器。替换磁盘上的二进制不会更新已经运行的进程。

```sh
journalctl --user -u clarion.service -f -o cat
python3 scripts/diagnose-latency.py --seconds 15 --output /tmp/clarion-latency.json
```

没有 systemd 用户服务时可传 `--pid PID`。采样时保持正常操作，最好在出现卡顿的相同应用、显示器和动效组合下采集；对比空闲与编译等高负载场景。

脚本只读取进程、系统压力和当前时间段的日志，写入新的 JSON 报告，不修改合成器或配置，也不会覆盖已有报告。包括进程 CPU、主线程调度等待和等待位置、大小缺页、VmSwap、进程读写字节、系统换入/换出及 CPU/内存/IO 压力。每个采样区间记录 PSI 累积停顿时间的增量；缺失或无法读取的计数不会伪装成零。

`latency_events` 保存去除终端颜色后的阶段与日志时间，`intervals[].latency_event_indices` 关联对应的一秒区间；`latency_logs` 保留文本形式。日志只查询被采样 PID 和采样时间范围，因此也适用于通过 `--pid` 指定的非 systemd 启动进程。关联时间是 journald 收到消息的时间，不等同于 GPU 呈现时间；聚合的 `max_ms` 与 `slow_samples` 可能包含更早几秒的样本。

系统 PSI 与 swap 计数包含其他进程。VmSwap 非零只表示仍有换出的进程内存，不能据此断言当前发生换页卡顿；应同时比较该区间的大缺页、系统换入量、IO 压力和慢阶段。进程 IO 计数也不是 GPU 内存访问统计。

注意：进程 CPU 统计包含其线程；调度等待只统计主线程。内核未启用调度统计时，零等待值不能证明没有竞争。采样窗口没有出现警告，也不能证明所有卡顿已消除。

## 如何进一步定位

- 渲染慢，fence-wait 也慢：继续检查 GPU 负载、跨 API 同步及调度等待；不能仅据此判定驱动故障。
- state-refresh、animation-update 或 client-dispatch 慢：在对应阶段缩小范围，再用已有 Tracy 支持验证。
- 主线程运行队列等待增加、系统 CPU 压力上升：对比其他负载和进程优先级，而非直接改动 GPU 同步。
- 卡顿发生时没有相应阶段报告：继续检查尚未覆盖的回调、事件队列延迟、输入设备和驱动路径。

## KMS 帧调度

HDR 色彩管理使用按实际输出缓冲保存的 FP16 场景。冷场景的异步准备会返回可重试状态，
此时保留交换链分配，只清除损伤历史；重置缓冲年龄也不能释放仍由 KMS/GPU 持有的槽位。
否则会形成“新目标需要准备 → 清空缓冲池 → 下一次仍是新目标”的循环，表现为持续的
`gpu_work_deferrals` 和隔帧呈现。普通渲染错误仍会丢弃内容未知的缓冲。
对比修复前后应检查热身后该计数的增量与实际呈现间隔，不能只以像素测试或 GPU 平均耗时验收流畅度。

HDR 输出的场景黑位按显示器参数换算，通常不为零。默认 SDR 窗口的感知黑白点适配
与场景 sRGB 编码归一化会相互抵消；仅因两个描述的黑位数值不同而逐帧转换整个窗口，
会增加 FP16 临时图像、色彩运算和分配压力。已知不透明 UNORM RGB 源可直接复用原纹理；
带透明度的源仍经过色彩 pass，只有采样值满足 `0 <= RGB <= alpha` 时才使用等价捷径。
PQ、scRGB、其他渲染意图和扩展范围像素继续使用完整转换。缓存未命中的 scratch 分配
也计入 `offscreen-allocation`，以免大窗口或分辨率变化的同步分配被隐藏在父阶段中。
验证应同时比较颜色、热身后的分配次数、CPU/GPU 工作和真实连续呈现间隔。

对于仍需转色的透明窗口，私有转色图像可以在同一 graphics queue 成功提交后按队列
顺序复用，屏障保证前帧读取早于后帧写入；GPU 完成对象继续保有图像所有权。
这避免多帧并行时按帧持有多组整窗 FP16 临时图像。截图、模糊和历史图像仍等待完成后
回收，两类复用共享原有八张／256 MiB 缓存上限；未提交的图像不会提前发布给后帧。

物理输出可用 `clarion msg frame-timings` 查看最近渲染耗时、预测呈现偏差和当前 latch 预算；`clarion msg --json frame-timings` 适合保存两次快照作比较。`late_presentations` 与 `fixed_refresh_presentations` 是累计计数，应比较同一输出在相同负载下两次快照的增量。没有历史呈现时间的首帧和缺少目标时间的帧不计入预测偏差。嵌套或无头输出不会使用 KMS latch 调度。

`kms_latch_delay_ms` 是计划等待时长，`kms_latch_wakeup_lateness_ms` 是定时器回调相对计划期限的实际晚醒时间（提前唤醒记为零）。若晚醒 P95 偏高，应先检查主线程负载和调度等待；若晚醒很小但硬件呈现仍迟到，应继续检查回调后的主循环处理、渲染、GPU 同步和 KMS 提交阶段。这个指标不包含回调后等待实际重绘及渲染所花的时间。

`kms_latch_to_render_delay_ms` 补充记录定时器回调到实际开始绘制之间的耗时，包括后续事件分发、状态刷新和其他输出占用主线程的时间，不包含绘制本身。一次唤醒只记录一次；显示时序变更取消等待后，不再沿用旧时间戳。旧版本 IPC 数据没有该字段时显示为缺失，不能当作零延迟。三个阶段分别统计分布，不能将各自 P95 相加当成端到端 P95。

固定刷新率下，预算先跟踪 CPU 渲染和提交耗时。若有硬件时间戳的帧比预测晚了超过半个刷新周期，调度器会逐步增加 GPU/KMS 完成余量；连续准时呈现后缓慢缩小余量。异步 Vulkan 提交的 CPU 耗时不包含后续 GPU 执行，原来的 4 ms／四分之一刷新周期余量上限会使部分本可按时完成的帧持续迟到。现在余量可以使用扣除 CPU 预算后的剩余刷新周期，总预算仍限制在一个刷新周期减去 250 微秒内；CPU 已耗尽预算时不再额外积累不可使用的余量。VRR 模式及模式切换后的首帧不会据此调整。回归模拟覆盖 60–360 Hz 的异步负载收敛、负载下降后的预算回落和 CPU 过载；这不代表实机 GPU 性能或输入到显示的延迟测量。此反馈不能消除 GPU 或驱动本身的瓶颈；应同时比较迟到率、渲染 P95 和主线程调度等待。

每次绘制最多等待一次 latch 定时器。定时器已触发后，即使主循环处理输入或其他输出导致错过原定刷新，也会立即准备绘制，并重新预测可呈现时间；不会把同一帧再次推迟到下一轮定时器。绘制尝试消耗这个就绪状态，显示模式或 VRR 状态改变则使其失效。回归覆盖晚醒、等待中合并输入、绘制失败后的复位和显示时序变更；真实 KMS 迟到率仍需登录新版后测量。

无画面变化的绘制也保留原定的模拟刷新回调期限。在等待该回调期间收到的新提交，可以合并到下一次 latch 绘制；两个定时器分别管理旧帧回调和新帧绘制。旧期限先到时，立即发送旧帧回调并释放其 FIFO 屏障，继续等待新帧的 latch；不得提前释放后来提交的 FIFO 屏障。模式切换只取消尚未执行的 latch 等待，输出移除则取消两个定时器。回归测试覆盖两种触发顺序、连续提交合并、取消与输出移除，并通过真实客户端提交验证 FIFO 释放顺序。

嵌套 Winit 输出没有宿主 VBlank 时间戳。无损伤帧现在保留唯一的预计刷新定时器，到期后才推进帧回调序号和继续动画；后来的空提交不会推迟这个期限。真实提交会取消旧定时器并立即进入下一序号，失败提交不会伪造一次刷新，输出移除会清理定时器。这能限制无损伤客户端的 `frame`/`commit` 循环，但它仍是按配置刷新间隔进行的近似节流，不代表与宿主合成器的真实 VBlank 相位对齐。

GLES 与 Vulkan 在等待 GPU 完成失败时，共用预计刷新后的重试调度。重试标志独立于动画是否结束，避免末帧被跳过后必须等新输入才能刷新。回归实际经过跳帧清理并验证后续补绘；这不等同于在真实 DRM 设备上注入 fence 中断。

GLES 与 Vulkan 在 KMS 拒绝提交时，也按输出独立安排重试。首次失败保持原来的预计刷新期限；连续失败后，从 50 ms 开始逐步退避，最长 1 秒。等待期间的新输入和客户端提交只合并到待绘制状态，在准备渲染元素前检查期限，避免绕过退避再次使用 GPU。已有的较早帧回调/FIFO 期限继续生效；期限到达后若还需要等待，会另设重试定时器。持续错误每个输出最多每 5 秒报告一次。成功提交或无损伤绘制清除退避，会话重新激活也立即清除退避并请求重绘。即使没有新输入或会话事件，定时重试仍会自动检查恢复；这一措施限制故障期间的无效工作，不修复 DRM 权限或驱动故障本身。回归覆盖提交风暴、健康输出、旧回调顺序、自动恢复和会话恢复，不在当前桌面主动撤销 DRM 权限。

输出移除时，VBlank 节流器会撤销尚未执行的延迟回调；即使回调正在执行并删除自己的输出，也能安全完成清理。真实硬件 VBlank 意外接管估算刷新等待时，会同时撤销旧估算定时器并保留必要重绘，避免旧回调在状态已经改变后触发不可达分支。离屏事件循环回归覆盖普通及已排队的估算等待状态、输出删除、回调内删除输出和正常提交决策；未在真实桌面注入显示器热插拔或异常驱动事件。

## 窗口总览的更新成本

窗口总览按工作区内的逻辑窗口顺序生成结果，不复用普通桌面的可见窗口列表。因此，离屏列、未激活标签，以及 Dwindle 全屏窗口背后的其他窗口仍可显示和搜索。绘制、命中检测、键盘选择和动画调度使用相同的搜索结果；可见缩略图的动画继续推进，搜索排除的窗口不再单独触发总览重绘。工作区背景切换和总览自身的过渡仍正常调度。

每次更新只为匹配的缩略图更新一次装饰，避免先套用桌面坐标和焦点、随后再改回缩略图状态，使静止边框每帧被错误标记为损坏。空查询不读取、复制和转换窗口标题；键盘选择也不再计算全部缩略图几何。工作区背景阴影单独更新，不依赖重复更新窗口装饰。

以下微基准对 128 个窗口的全部结果、单个结果、空结果分别测量装饰更新阶段；不包含 GPU 绘制、呈现和端到端输入延迟。前后比较必须使用相同编译配置和尽量一致的系统负载。

```sh
cargo test --locked -p clarion --lib layout::tests::spread::spread_update_cost_microbenchmark -- --ignored --nocapture --test-threads=1
```

装饰损坏计数回归使用渲染节点创建离屏环境，验证静止帧保留计数、切换选中项仍产生必要损坏；不取得 DRM 显示控制权。把下面路径替换为实际渲染节点：

```sh
CLARION_VULKAN_TEST_NODE=/dev/dri/renderD128 cargo test --locked -p clarion --lib layout::tests::spread::spread_static_decorations_keep_damage_counters -- --ignored --nocapture --test-threads=1
```

## 手势与多屏交互

总览中的双指滚动按首个非零事件的主轴锁定方向：水平位移较大时横向滚动，纵向位移较大或相等时纵向切换工作区。同一次手势保持锁轴，双零停止事件和取消保持原有结束语义。滚动快捷操作的零位移事件保留最后的非零方向；停止后反向滚动时，会先丢弃旧方向的残余，避免第一次反向输入被抵消。回归覆盖正负方向、零样本、重新开始及小数累计。

滑动惯性按首末采样之间的已知位移估速。每次事件的位移止于该事件的时间戳，因此最早保留样本的位移属于区间之前，不应加入分子；否则两个相隔 10 ms、各移动 10 单位的样本会误算成 2000 单位/秒，现在按已知区间计算为 1000。相同时间戳的事件合并，避免同一批输入的拆分改变速度；全部有效位移仍计入实际位置，150 ms 历史窗口和减速系数不变。停住至少一个历史窗口后收到结束时的零样本，惯性归零；只有一个采样时刻时无法估速，也不推断惯性。回归覆盖短甩、同时间戳拆分、历史裁剪、停顿松手、立即松手及逆序事件。

最近窗口列表的缩略图、选中项和筛选动画只维持所属输出的刷新。列表在所有输出绘制遮罩，因此延迟显现、淡出及淡出途中重新打开仍会刷新所有输出。移除所属显示器时立即释放打开中或淡出中的列表，保留筛选范围，并请求其他屏幕刷新以清除遮罩；移除其他显示器只清理它的遮罩缓存。回归同时覆盖活跃和空闲调度、跨屏重开、窗口帧回调及屏幕移除。

进入空闲状态后，拖动仍按所属输出判断是否需要连续绘制：拖拽内容和平铺窗口保留边缘滚动调度；浮动窗口在移动动画收尾后可以停止连续绘制。仅按下但未开始移动的窗口由工作区内实际动画决定。其他输出上的真实过渡和全局总览动画仍正常推进。回归检查拖动跨屏后的归属切换、静止浮动窗口、局部动画重新启动、总览过渡和结束后的边缘滚动。

## 首次 Vulkan 绘制

输出格式协商完成后，预热该格式和 RGBA8 离屏目标的标准绘制管线及已有自定义动画管线。初始化默认 BGRA8 管线并不能覆盖 RGBA8 效果、截图或协商为 10-bit 的输出；缺少预热时，首次实际绘制会同步创建标准管线。其他格式仍按需建立，同一格式重复预热复用缓存。代价是把这些管线的准备工作提前到输出初始化或恢复阶段，不能据此推断某次日志中的长帧已被消除。

新增 GPU 回归在未加载自定义着色器时验证预热，并对 RGBA8 与 10-bit 目标执行真实绘制、像素读回和重复调用句柄复用检查。它不切换实际显示模式，也不证明当前显示器正在使用 10-bit：

```sh
CLARION_VULKAN_TEST_NODE=/dev/dri/renderD128 cargo test --locked -p clarion --lib native_output_prewarm_builds_standard_formats_before_first_draw -- --ignored --nocapture --test-threads=1
```

## 内存占用与泄漏排查

```sh
python3 scripts/diagnose-memory.py --seconds 300 --interval 5 --output /tmp/clarion-memory.json
```

报告同时记录合成器进程的 RSS/PSS/匿名内存、打开的 fd 数量，以及所在 systemd 服务 cgroup 的匿名内存、文件缓存和共享内存。`memory.stat` 的 `file` 已包含 `shmem`，不能把这些字段相加。服务 cgroup 还包含 Xwayland 等子进程及共享缓冲区，不能把它的总量直接当作 Clarion 的 Rust 堆占用。先记录空闲基线，再用固定操作重复创建和销毁窗口、录屏或热插拔；操作结束后继续采样，比较进程匿名内存、fd 数和 cgroup 共享内存是否回落。短时间增长可能来自正常缓存或驱动分配，单次采样无法证明泄漏；GPU 显存也未必完整反映在这些计数中。


## 高性能与动画流畅度的验收方向

项目以低渲染开销、稳定呈现节奏和连续跟手的动画为共同目标。macOS 级体验是体验目标；单元测试、平均 FPS 或某次微基准通过，均不代表已完成对等体验验收。

- **帧预算**：60 / 120 / 144 / 240 Hz 每帧分别约 16.67 / 8.33 / 6.94 / 4.17 ms。CPU 渲染与提交 P95 以不超过该预算的 25% 为优化目标，为 GPU、客户端和系统调度留出余量；同时观察最大值与迟到率，避免平均耗时掩盖尖峰。
- **运动连续性**：拖动、缩放、概览、工作区切换和画布惯性不应因刷新率改变而出现重复运动帧、跳变或不同的滑行终点。弹性窗口保持固定物理步长，在步间计算显示位置；惯性按真实经过时间积分。相同呈现时间被重复读取时，物理状态不得再次推进。
- **空闲成本**：动画静止后停止持续计算和重绘；已稳定的网格继续复用缓存。关闭动画和降低效果的用户设置仍需生效。
- **比较条件**：使用相同屏幕、缩放、窗口尺寸和工作负载，分别测量空闲、持续拖动/缩放、反复开关窗口、概览切换，以及编译等负载下的表现。记录版本、显示模式和前后两份 `frame-timings`，比较计数增量；CPU 渲染耗时不能当作 GPU 耗时或输入到显示的延迟。

高刷新率模拟回归覆盖窗口弹性动画至 360 Hz、画布惯性从 30 到 360 Hz。真实硬件只按实际连接的刷新率验收；60 Hz 面板上的结果不能证明 120/240 Hz 的端到端流畅度。输入到显示的延迟、触控板跟手感和与 macOS 的直接对照仍需固定操作场景下的实测。

### 动画过渡的细节

体验对比先使用 `animations { slowdown 1.0; }`。缩短时长会减少可见帧数，不能代替稳定呈现、连续速度和自然收尾。开窗 320 ms、破碎关闭 400 ms 的配置时长保持不变。

- 默认弹簧动画在连续切换工作区、反向开关总览、横向切换焦点、重排窗口和最近窗口列表移动时，承接当前运动速度。反向操作会先减速再转向；位移正好抵消时也不能把余下速度丢掉。
- 开窗在首个缓冲区映射后直接进入 320 ms 展开过程，移除额外的 64 ms 固定等待；客户端缓冲区和 GPU 同步仍走原有的 fence 路径。模拟首帧反馈覆盖 60–360 Hz。
- 总览缩放与工作区切换同步时，在连续缩放坐标中计算位置和速度。打断时一并继承缩放造成的速度变化，避免将原始位移速度误用于屏幕上的运动。
- 提示内容重复更新时保留可见位置；提示和退出对话框反向播放时保留速度。重复隐藏请求不会延后同一次退出动画的结束。
- 拖动松手后，窗口从当前可见透明度和速度恢复不透明；重复恢复请求不重启动画。透明度始终限制在 0–1，越界后不可见的弹簧速度不带入下一次过渡。
- 最近窗口列表在同一输出上淡出期间重新打开时，承接当前透明度与速度，复用绘制资源并刷新窗口顺序。仍可见的列表不重新等待首次打开延迟；完全关闭后或跨输出打开时保留原有延迟。缩略图改目标时也承接原来的位移速度。
- 连续缩放和全屏切换分别继承窗口宽高、外框宽高和装饰进度的速度；即使新目标恰好落在当前尺寸，也保留尚未消散的运动。尺寸回归检查实际快照提交路径及 60–360 Hz 下的连续性。新尺寸真正生效时，再将正在显示的旧混合画面合成为新过渡的起点；等待 acquire fence 或事务期间，旧动画继续推进，不把等待前的旧进度带回屏幕。
- 连续缩放所需的旧客户端内容在替换渲染缓冲区之前复制为合成器自有纹理，完成复制后才允许旧存储释放。复制结果直接作为纹理缓存，避免再复制一次；中途打断的混合画面只拍平一次，不保留递归动画链。显示、录屏、截屏分别遵守各自的遮挡规则，窗口透明度与圆角在最终绘制时应用。 客户端使用单像素纯色缓冲区时，也会生成对应的纹理内容，保留透明度和 viewport，避免快照空白或缩放动画丢失。
- 快照记录实际捕获倍率，跨不同缩放的输出时按原像素网格采样，保留窗口阴影的负偏移。默认缩放着色器在输入纹理外采样时返回透明，避免下一目标的阴影范围更大时把旧图边缘拉成色边。真实 GPU 回归检查打断前后的像素、半透明内容、跨倍率和客户端复用旧缓冲区的情况。
- 最近窗口列表淡出时，只有实际呈现的离屏纹理才把内部缩略图标记为可见，继续给对应客户端发送刷新与呈现反馈。跨输出缩略图也参与反馈；所属输出仍显示窗口时，保持所属输出的节奏。录屏、截屏的绘制不覆盖屏幕可见性记录。
- 透明度按实际可见终点结束重绘，避免欠阻尼弹簧已经显示为完全透明或不透明后继续空转。最近窗口列表布局没有位移时保留原动画期限；缩略图内容、背景和高亮边框同步淡入。隐藏的标签指示条停止动画，重复展开时继承当前进度。
- 画布的新手势在第一个输入样本就接管旧惯性并保留该次位移，等待第二个样本建立新速度；短暂反向触碰不会继续沿上一手势方向滑动。30–360 Hz 回归验证滑行终点一致且停止后不再请求绘制。
- 触摸移动和缩放会在主触点抬起前应用同一硬件帧里的最后一次位移。副触点和空触摸帧只完成协议帧，不重放主触点的旧缩放量；嵌套 Winit 为每个原子 Down、Motion、Up 事件补齐帧边界，使拖动及时反馈。
- 概览中的触摸和数位笔抬起也先消费尚未处理的移动，再判断轻点或结束拖动，避免末帧滑动被误判成点击、拖动落点退回上一帧。取消、替换手势或数位笔离开感应范围不会触发轻点激活；已开始的手势仍正常收尾。触摸回归覆盖横向/纵向滑动、拖动末帧、副触点、取消和正常轻点。
- 动画光标只有在可见且任一动画帧实际覆盖输出时才维持该输出刷新。所有帧的联合边界按光标倍率缓存，并保留跨输出、数位板位置和分数缩放边缘的一像素取整余量；隐藏或禁用光标不再产生空重绘。
- 速度按真实时间传递，再由动画时钟换算，避免设置慢放或恢复正常速度后重复缩放速度。自定义定时缓动仍按用户指定曲线播放。
- 弹簧仅在位置和速度的衰减包络都达到阈值时结束，避免经过目标点就停住或结尾跳到终点。不同距离的同步动画使用相同的相对精度；重阻尼使用两个衰减项直接求值，避免数值溢出。
- 回归测试检查切换前后的连续位置与速度、60–360 Hz 的打断时序、原地改目标、关闭动画和慢放。实际体验还需观察开窗、总览半途取消、连续换工作区和窗口重排，不以单次顺向播放代替打断测试。

可用下面的微基准检查弹性网格计算成本（单位为微秒），它不包含 GPU 渲染、输入队列或 KMS 提交：

```sh
cargo test --release -p clarion --lib layout::wobble::tests::dynamic_mesh_frame_cost_microbenchmark -- --ignored --nocapture --test-threads=1
```

## 弹簧动画初始化成本

水平视图和工作区切换继续采用临界阻尼默认值，窗口移动和缩放已采用轻微欠阻尼的
交互参考配置。欠阻尼的完整收敛截止期直接求位置、速度指数包络的对数解，包含初速度，
不再为每次创建或重定向执行包络二分。临界与过阻尼保留有界搜索，保守向上取整避免提前终止。
旧的整数毫秒目标到达接口保留兼容行为；动画的首次目标到达另按连续时间处理，避免高刷新率
和慢放倍率下一个整数毫秒内的超调。详见 [方案实施记录](macos-animation-scheduling.md)。

回归将新结果与旧扫描逐项比较，覆盖正反向移动、初速度反向、不同刚度和容差、零位移、退化参数及截止边界。以下独立优化构建可重复运行计算微基准，不需要打开显示会话：

```sh
clarion_spring_wrapper=$(mktemp /tmp/clarion-spring-wrapper.XXXXXX.rs)
printf '#[path = "%s/src/animation/spring.rs"] mod spring;\n' "$PWD" > "$clarion_spring_wrapper"
rustc --crate-name clarion_spring_tests --edition=2021 --test -O "$clarion_spring_wrapper" -o /tmp/clarion-spring-tests
/tmp/clarion-spring-tests
/tmp/clarion-spring-tests clamped_search_initialization_microbenchmark --ignored --nocapture
rm -- "$clarion_spring_wrapper"
```

微基准只测 128 个默认临界阻尼弹簧的目标时间计算，交替运行旧扫描与新查找并报告中位数。它不包含 GPU 渲染、呈现或端到端输入延迟，也不意味着全部动画路径或整帧耗时会按同一比例下降。

本轮另测实际的“完整收敛截止期 + 连续首次到达截止期”初始化路径：128 个
`.92 / 300 / .001` 弹簧、混合方向与初速度，9 轮交替测量的中位数为 76.957 微秒；
原 40 次包络二分与逐毫秒扫描为 1192.206 微秒。新连续到达计算比中间版整数毫秒
快速路径多约 0.21 微秒/动画，用于消除高刷新率边界误差。这仍不是整帧或输入延迟测量。

## 原生调整大小快照的队列衔接

`freeze_native` 不在客户端 commit 回调中重复等待复制 fence。原生渲染器提交时已持有
采样到的 Wayland 缓冲区及源/目标图像，后续采样通过同一 graphics queue 和图像屏障排序。
完成任务在 GPU 实际完成后释放所有者；没有可用缓冲区所有者的导入继续同步回退。
GLES 通用冻结路径的等待保持不变，不能通过直接删除等待来解决它的缓冲区寿命问题。

这项修改减少了原生缩放提交中的同步阻塞，不证明它是此前所有桌面停顿的根因。
需要新会话的同场景帧时间与输入记录才能评估端到端收益。
