# 2026-10-18 HDR、Vulkan 与多显卡审计

## 结论与范围

当前 TTY 桌面确实由原生 Vulkan 合成，并通过 KMS 输出 HDR；仍有流畅度优化空间。窗口总览、工作区切换和大面积 SHM 客户端更新没有全部达到验收阈值。原生 Vulkan 后端也不能等同于所有硬件路径均已完成：目前没有按显卡独立的原生渲染器，NVIDIA 的三个 CPU-dumb NV12 互操作探针仍失败。

本次物理桌面测量基线为 `ce87b9e`，进程 PID 1300。测试没有重启合成器或注销会话。环境为 Intel Iris Xe（ADL GT2）、Mesa 26.2.5，eDP-1 3840×2400、约 60 Hz、缩放 2、10 bpc HDR。机器另有 NVIDIA RTX 2050、驱动 615.78.08，用于独立的 Vulkan 导入、绘制和同步测试；没有连接到 NVIDIA 的外接显示器。因此没有复现其他使用者的双屏物理拓扑，也没有证明其问题已修复。

## 物理 HDR 会话测量

使用 `scripts/verify-frame-budget.py` 每 150 ms 采集累计序号及原始样本。总览和工作区各往返 10 次、每组 25 秒；启动器开合、窗口缩放和全屏切换各往返 8 次、每组 17 秒。测试后关闭临时窗口并恢复工作区及焦点。

| 场景 | CPU 绘制/提交墙钟 P95 | 主线程 CPU P95 | 连续活动长间隔 / 有效间隔 | 原生输出命令缓冲区 GPU P95 |
|---|---:|---:|---:|---:|
| 普通桌面观察 | 0.633 ms | 1.965 ms | 0 / 170，0% | 5.634 ms |
| 窗口总览 | 1.272 ms | 3.234 ms | 52 / 762，6.82% | 11.883 ms |
| 工作区切换 | 2.195 ms | 3.041 ms | 44 / 551，7.99% | 样本不完整 |
| 启动器开合 | 0.952 ms | 2.658 ms | 0 / 437，0% | 7.185 ms |
| 临时 SHM 窗口缩放 | 6.782 ms | 8.803 ms | 43 / 878，4.90% | 样本不完整 |
| 临时 SHM 窗口全屏往返 | 20.729 ms | 24.389 ms | 265 / 615，43.09% | 样本不完整 |

“长间隔”采用脚本对固定刷新输出连续活动的定义，不是整段录像的丢帧率，也不是输入到显示的延迟。CPU 绘制/提交包含驱动调用的墙钟等待；主线程 CPU 则覆盖两次连续呈现之间的主线程实际运行，两者不能相加。GPU 时间只覆盖该输出命令缓冲区，不覆盖整帧所有上传、离屏工作或 KMS 扫描输出。

普通桌面为被动观察，不能证明所有交互均流畅。缩放和全屏使用独立 `foot` 窗口，以约 30 次/秒清屏更新，属于大面积软件 SHM 上传压力测试，不能代表所有 GPU 渲染应用。全屏重复采样仍出现约 17.7 ms 的 CPU 绘制/提交 P95，说明问题可再次触发，但此轮未得到可用的 CPU 调用栈：系统权限拒绝了 `perf record`。没有修改系统安全设置，也没有把失败的采样当作性能证据。

启动器测的是启动器本身，未启动其他应用。8 次 Show 请求的 Visible IPC 响应约为 21.9–133.2 ms；该确认不是首帧呈现时间。工作区、缩放、全屏分别记录 43、29、23 次 GPU 延后重试。缺失 GPU 样本的场景不发布全程 GPU P95，也不以末尾滑动窗口的分位数代替全程结果。

## 本次修改

### 用实测 GPU 时间辅助固定刷新预算

原来的 Vulkan 时间戳只用于诊断，调度主要依靠 CPU 时间和迟到呈现反馈。CPU 提交很短时仍可能留下十余毫秒的 GPU 工作，负载变化需要等多次迟到才能学到足够预算。

现在按输出接收已完成的命令缓冲区时间，保留 GPU 耗时加 250 微秒的预算下限。增长立即采用、下降逐步回落；与呈现反馈推断的尾部余量取较大值，避免重复相加。总预算继续受刷新周期限制，旧序号、模式切换前提交和错误输出代次的样本不调整新预算。VRR 不使用这条固定刷新率规则。

60/120/144/240/360 Hz 的合成负载回归中，1200 帧内的预测迟到次数分别由 13/11/11/10/9 降为 7/6/6/5/5。这是调度模型结果，不是物理桌面的改善幅度，也不能解决本身超过帧周期的 CPU/GPU 工作。

### 复用 SHM 上传前的 CPU 快照

发现每次受损 SHM 导入都会重新分配临时像素 Vec，复制完成后再复制到 Vulkan staging。4K 大窗口会不断分配数十 MiB。现在每个原生渲染器按需复用一块 CPU 快照，最多保留 64 MiB；大于上限的上传仍支持，但导入结束后不保留大块存储。普通错误路径也会回收可复用存储。

保护边界保持不变：不构造指向客户端可写内存的 Rust 引用；通过 Smithay 保护原始读取；只有成功完整复制后才设置 Vec 长度；局部损伤仍有裁剪和互不重叠检查。Vulkan 上传在返回前取得独立 staging 副本，GPU 尚未完成时也可复用 CPU 快照。

在没有并行编译的第二轮 3840×2400 RGBA 复制微基准中，三组各 80 次，重新分配的 P50 为 5.14–5.22 ms、P95 为 6.49–8.05 ms；复用为 P50 1.93–2.74 ms、P95 2.30–5.22 ms。每组预热后的 minor faults 从 25,121 降至 0。第一次并行编译期间的测试更慢，不用它作为稳定基线。这只隔离 CPU 临时分配和复制，不包含 staging 上传、GPU、窗口动画或呈现。

已有真实 Wayland SHM 回归扩展为：GPU 队列被阻塞时，立即覆写已回收的 CPU 快照，再检查最终像素；覆盖缓冲区轮换、局部/空/越界损伤、格式切换、DMA-BUF 与 SHM 切换、错误后的复用和超限缓存释放。增加 `vulkan-shm-import` 慢阶段日志，为后续物理复测提供更具体的归因。

### 项目检查和版本诊断

修复严格 Clippy 检查发现的未使用导入、可派生 Default，以及 vendored GPUI 的两个模糊浮点字面量；统一已有格式偏差。桌面健康检查改为比较当前 PATH 启动版本与运行中的二进制，避免把旧 `/usr/local/bin` 副本误认为当前启动版本而反复提示注销。全局副本不同仍会单独提示。

## Vulkan 实现与双显卡限制

`Tty` 只有一个 `native_renderer`，`with_renderer_for_output` 选择原生 Vulkan 或 GLES 路径，不会为不同显卡建立独立 Vulkan 上下文。次显卡输出的原生路径使用主显卡 allocator 和线性 DMA-BUF，再交给目标显卡的 KMS。启动日志中的 `uses Vulkan composition on render node …, KMS scanout on …` 可确认实际渲染卡与扫描输出卡。

这不是“内屏 Intel 渲染、外屏 NVIDIA 渲染”。高分辨率下跨卡缓冲区共享、驱动内部访问/搬运与同步的成本可能放大。指定主渲染卡只是改变共享方向；它不会自动消除另一块屏幕的兼容性要求，也不能从症状直接证明存在 CPU 逐帧拷贝。

创建输出时会探测 KMS swapchain 与 Vulkan 目标导入，不兼容时尝试 GLES。一旦发布颜色管理协议，就拒绝需要 GLES 的输出，以免已经接受的 HDR 客户端颜色被错误解释。这是主卡切换后另一块屏幕不显示的一个可能路径；还需实际日志确认失败点，不能把它当作其他使用者黑屏的已证实原因。

真正的每卡独立渲染需要按 render node 管理上下文、allocator 和提交队列，按输出路由纹理导入与客户端 DMA-BUF feedback，处理窗口跨屏时的图像/动画快照迁移，并维护每张卡的颜色管理和设备恢复。此次没有实现这项架构改造，也没有通过禁用 HDR 或降低颜色精度绕过它。

原生 Vulkan 已覆盖 TTY 合成、无头绘制和嵌套 WSI；保留的 GLES 兼容路径、SHM CPU 复制及截图读回仍存在。HDR 托管合成暂不启用直接扫描输出和 overlay，HDR 光标仍合成。ICC、HLG、通用 YUV range/chroma-location、完整 HDR 捕获元数据和 HDR 夜间色温等限制见 [HDR 文档](hdr.md)。

## 硬件验证与未解决项

使用匹配的 Intel/NVIDIA ICD、`VK_LAYER_KHRONOS_validation` 和同步校验，逐卡测试，不获取显示 master。

最终 `scripts/check-project.sh --offline` 通过：模块边界、shell 语法、109 个 Python 测试、格式检查、完整工作区 1756 个 Rust 测试（189 个 ignored）和全目标严格 Clippy。新增慢阶段最初遗漏了计数器枚举回归中的条目，完整检查发现后已补齐并重新通过。依赖 `proc-macro-error2 2.0.1` 仍有未来 Rust 兼容性提示，未在本次升级该依赖。交互式视觉测试程序参与编译，但未人工运行它的界面验收。

- Intel Vulkan 命名空间 229 项通过；8 个无头/Wayland/颜色集成均通过。
- NVIDIA Vulkan 命名空间 226 项通过、3 项失败；另外独立运行的 8 个集成全部通过。
- SHM 复用修改后，两张卡各重新验证 12 个相关用例，全部通过；包括 CPU/协议辅助测试，不能称为 12 个 GPU 场景。
- 上述日志未出现 VUID 或同步校验错误。可选的 disjoint NV12 能力缺失与特定设备探针未执行单独记录，不算硬件覆盖。

NVIDIA 三个失败仍是 CPU-dumb 线性 NV12 路径：16×16、pitch 16、UV offset 256 的 4 KiB 分配小于驱动要求的 128 KiB，因此被拒绝；仅增加 backing 大小仍得到错误像素。真实 GPU 生产的 NV12（本轮 pitch 128、UV offset 65536）通过像素和同步验证。默认完整检查保持失败，不删测试、不用 RGB/HDR 子集冒充全通过。该问题不能直接归因于当前 Intel HDR 桌面的卡顿。

常规工作区测试不自动执行被标记 ignored 的真实硬件测试。交互式视觉测试界面、其他使用者的双屏热插拔/混合刷新率、休眠恢复和端到端输入延迟没有完成物理验收。短时 RSS、匿名内存和 fd 采样也不足以判定长期泄漏。

本次修改后的物理 KMS 流畅度还需要在新版合成器会话复测；安装替换下次启动入口不会改变已运行的 `ce87b9e` 进程。当前结论是确认两处可修复的成本并完成代码与回归，尚不能宣布所有 HDR 场景流畅或双显卡问题已解决。

## 复现入口

```sh
scripts/check-project.sh --offline
VK_DRIVER_FILES=/usr/share/vulkan/icd.d/intel_icd.json scripts/check-vulkan.sh /dev/dri/renderD128
VK_DRIVER_FILES=/usr/share/vulkan/icd.d/nvidia_icd.json scripts/check-vulkan.sh /dev/dri/renderD129
python3 scripts/verify-frame-budget.py --seconds 30 --interval .15 --scenario 'HDR overview' --outputPath /tmp/clarion-hdr-overview.json
```

设备节点与 ICD 需按机器实际情况替换。双显卡反馈可先保留默认主卡与指定主卡两种配置下的 `clarion msg --json outputs`，以及本次启动日志中的 `Vulkan`、`KMS`、`render node`、`fallback`、`hotplug` 和 `color management` 信息，核对渲染与扫描输出所在设备及拒绝原因。
